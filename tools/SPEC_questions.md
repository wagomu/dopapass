# 問題データ仕様

アプリは `data/past.json` と `data/original.json` を読み込む。どちらも **問題オブジェクトの配列**（UTF-8 / JSON）。

## 問題オブジェクト

```json
{
  "id": "R06-003",
  "source": "past",
  "year": "令和6年度",
  "no": 3,
  "field": "strategy",
  "category": "経営戦略",
  "q": "未来のある時点に目標を設定し，そこを起点に現在を振り返り，目標実現のために現在すべきことを考える方法を表す用語として，最も適切なものはどれか。",
  "table": null,
  "choices": ["PoC（Proof of Concept）", "PoV（Proof of Value）", "バックキャスティング", "フォアキャスティング"],
  "answer": 2,
  "explain": "…",
  "credit": "出典：令和6年度 ITパスポート試験 公開問題 問3",
  "modified": false
}
```

| キー | 説明 |
|---|---|
| id | 過去問: `R06-003` 形式（年度2桁-問番号3桁）。オリジナル: `O-S001`（S/M/T + 連番） |
| source | `"past"` か `"original"` |
| year / no | 過去問だけ使う。オリジナルでは `null` |
| field | `strategy`（ストラテジ系）／`management`（マネジメント系）／`technology`（テクノロジ系）。過去問は 問1–35 → strategy、問36–55 → management、問56–100 → technology |
| category | シラバスの中分類くらいの粒度の短いラベル（例: 経営戦略、法務、プロジェクトマネジメント、セキュリティ、ネットワーク、データベース、アルゴリズム、ハードウェア …） |
| q | 問題文。原文に忠実に書く。読点は原文の「，」のままでよい。改行は `\n`。下線部や空欄 `[ a ]` などはテキストで表す |
| table | 問題文中の表を文字にできる場合の2次元配列 `[["見出し1","見出し2"],["値","値"]]`。1行目を見出しとして扱う。不要なら `null` |
| choices | 選択肢4つ（ア, イ, ウ, エ の順）。先頭の「ア」などの記号は**付けない**。組合せ問題は `"a: 〇〇 / b: △△"` のように1行で書く |
| answer | 正解のインデックス（0=ア, 1=イ, 2=ウ, 3=エ） |
| explain | 解説（下記トーンガイドに従う） |
| credit | 過去問: `出典：令和6年度 ITパスポート試験 公開問題 問3`。オリジナル: `"オリジナル問題"` |
| modified | 原文を改変した場合は `true`（表を文字にした、図の情報を文章で補った、など）。アプリ側で「（改変あり）」と表示する |

## 過去問の除外ルール
- 図（グラフ、フローチャート、ネットワーク図、画面イメージ、ベン図など）を見ないと解けない問題は **除外** する。
- 単純な表は `table` に書き起こして `modified: true` にすれば収録してよい。
- 除外した問題は、別ファイルで `{"id": "R06-057", "reason": "フローチャート"}` の配列にして返す。

## 解説のトーンガイド（ドパガキ向け）
- 2〜4文、だいたい80〜180字。**正確さが最優先**で、ノリはその次。
- 最初の一言でテンションを上げる（毎回同じにしない）。例: 「これは秒で取りたい」「ガチで頻出」「ひっかけ注意⚠️」「わかりみ深い」「優勝問題」
- そのあとに、なぜそれが正解か → 他の選択肢が何の説明か（主要なものだけ短く） → 覚え方（あれば）、の順で書く。
- 使ってよい言い回し: それな / 草 / 神 / ガチ / エグい / ワンチャン / 沼 / 優勝 / 秒で / 〜しか勝たん / 完全に理解した
- 絵文字は1解説につき0〜2個まで。下品な表現、差別的な表現、特定の人物をいじる表現は使わない。
- 計算問題は、途中の式を簡潔に書く（例: `2,000 × 0.3 = 600`）。

例:
> 未来から逆算＝**バック**キャスティング、ガチ頻出🔥 ゴールから「じゃあ今なにする？」を考えるやつ。フォアキャスティングは逆で、今の延長で未来を予測する方。PoC は技術的に実現できるかの検証、PoV は価値があるかの検証な。
